1. The honest state of things

You're inheriting a quality setup that grew under deadline pressure and never got cleaned up. Before you trust anything, assume it's wrong until you've checked it. The headline problems:

  • The Playwright framework (brislane-lending-platform) is flaky and slow. People stopped trusting it months ago and started merging on red.
  • CI is currently failing on main and has been amber/red for weeks. NOT DOCUMENTED why it started failing — see section 4.
  • Test coverage of the loan journey is patchy. The early stages are covered; the later stages (the important ones) are mostly manual or not covered at all.
  • The Postman collection is out of date and the auth is set up wrong (see section 5).
  • There are no quality metrics. Nobody can tell you the real pass rate, defect leakage or coverage. Leadership has been guessing.

2. The loan journey — test process by stage

The journey is: APP_START → ID_VERIF → DOC_UP → AFF_CHK → CR_DEC → SUBMIT → FUND.

I only ever fully documented the front half. Here's the truth stage by stage:

Stage 1 — APP_START (application started)

Documented. Smoke test exists (tests/loan/start.spec.ts). Stable. Reasonable selectors.

Stage 2 — ID_VERIF (identity / KYC)

Documented. Uses a sandbox KYC provider in DEV/QA. Test data in test-data/kyc/. Works but slow — there's a hardcoded waitForTimeout(5000) in there I'm not proud of. CHECK THIS — that wait is a big source of flakiness.

Stage 3 — DOC_UP (document upload)

Partially documented. Upload works in QA. There's a known issue where the upload spinner sometimes never resolves on WebKit — I logged it but never root-caused it. The automation for this stage uses a duplicated selector that also exists in the payments page object. DEPRECATED? — I think OldUploadPage.ts is dead but I'm not certain; grep before you delete.

Stage 4 — AFF_CHK (affordability check)

NOT DOCUMENTED. There's no automated coverage. I tested this manually. The business rules for affordability live in someone's head (probably Product). You'll need to get these written down — they're a compliance-relevant control.

Stage 5 — CR_DEC (credit decision)

NOT DOCUMENTED. No coverage. This calls an external credit bureau in UAT only — it's mocked nowhere, which is why we can't test it reliably below UAT. CHECK THIS — mocking this is probably your biggest framework job.

Stage 6 — SUBMIT (final submission)

NOT DOCUMENTED and this is the one that's on fire. Submit failures have been climbing and I never got to the bottom of it. There's a half-written spec (tests/loan/submit.spec.ts.skip) that's been skipped for two sprints because it's flaky. See section 7 — this is my unfinished business and probably yours on day one.

Stage 7 — FUND (funding / approval)

NOT DOCUMENTED. No coverage at all. Funding writes to the ledger and the audit log. Compliance care about the audit log a lot (David will tell you). Nobody validates it today. CHECK THIS against the database.

4. The automation framework (brislane-lending-platform)

What's there:

  • playwright.config.ts, src/pages/ (page objects), tests/, api/, fixtures/, utils/, test-data/, .github/workflows/.

What's wrong (the stuff you'll refactor in the framework phase):

  • Hardcoded waits everywhere (waitForTimeout) instead of proper auto-waiting. Main flakiness driver.
  • Duplicate selectors across page objects (login + payments share copy-pasted locators).
  • Broken assertions — some specs assert on stale text and pass for the wrong reason.
  • Flaky tests — submit + upload specs fail intermittently; people retry until green.
  • Poor naming — test1.spec.ts, newtest.spec.ts, you get the idea.
  • Missing fixtures — auth state is re-created per test by logging in through the UI every time (slow, and ironically relevant to the submit problem — see section 7).
  • Weak Page Object design — pages expose raw locators, no encapsulation.
  • Unused code / duplicate utilities — two date helpers, one unused logger. DEPRECATED? throughout utils/.
  • Failing CI — .github/workflows/ci.yml is red. NOT DOCUMENTED exactly why it broke; it started after a dependency bump. No quality gates configured.

5. APIs / Postman

  • The collection (postman_collection.json) covers Auth, Customers, Loans, Payments, Notifications but it's stale.
  • Auth is set up wrong — the collection hardcodes a bearer token that's long expired, so half the requests 401 out of the box. CHECK THIS — needs a proper login request + token variable.
  • There's no negative testing and no contract validation. Status codes aren't asserted.
  • Compliance-relevant: there's no test that an expired or tampered token is correctly rejected, and nothing exercising SCA on payments. David will flag this hard — get it into scope.
  • NOT DOCUMENTED — rate limiting behaviour. We think /loans/submit and /payments are rate limited (429) but nobody's confirmed the thresholds.

6. Environments

  • We run DEV, QA and UAT. Config is currently scattered across .env files that aren't all committed (some live on my laptop — sorry, Sandra has copies).
  • NOT DOCUMENTED — the full list of secrets/variables per environment. Sandra (SRE) is your source of truth. Get her to walk you through the gateway and the auth service config.
  • UAT is the only env wired to the real credit bureau. DEV/QA mock it inconsistently. CHECK THIS.

7. The thing I never got to (my hunch — please chase this)

This is the one that's been bugging me. Submit failures started climbing around early-to-mid June and they never came back down. At the same time, customer complaints about "the page failing when I submit" and "getting logged out" went up.

Here's my unproven theory, for what it's worth:

  • The auth team shipped a release to the authentication service around 8 June — the deploy reference I saw in the logs was AUTH-SVC 2.4.0. I'm fairly sure it changed the access-token lifetime (TTL).
  • The loan application is a *long* form. My hunch is that on the slower journeys the token is expiring before the user reaches submit, so /loans/submit 401s, and the UI shows a generic "submission failed" error — which looks like an upload or form problem but isn't.
  • I never proved it. I was buried in release work. CHECK THIS — cross-reference the API error log (brislane_operational_report.csv) against the funnel (brislane_primary_data.csv) and the support tickets (brislane_secondary_data.csv), and look at what kind of failure dominates /loans/submit after that deploy. If I'm right it's an auth/session issue, not a UX one. If I'm wrong, ignore me — but the data should settle it either way.

Either way: don't take my word for it. Prove it with the numbers.
